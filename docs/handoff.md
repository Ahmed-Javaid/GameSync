## How to work

```powershell
dotnet build GameSync.sln
dotnet test GameSync.sln
# The app on a scratch data folder, so nothing of the owner's is touched (see below for making one).
& src\GameSync.App\bin\Debug\net10.0-windows10.0.19041.0\GameSync.Tray.exe --data <scratch>
# Render pages to PNG files: the component galleries, or Home and the library from a data folder's games and art.
dotnet run --project tools/GameSync.Snapshots -- <output folder> gallery gallery2 gallery3
dotnet run --project tools/GameSync.Snapshots -- <output folder> --data <data folder> home library library-full library-hidden
# The real window in Glossy over the last-played game's art, one per strength (light mode shows it Solid).
dotnet run --project tools/GameSync.Snapshots -- <output folder> --data <data folder> glossy-home glossy-library glossy-console glossy-settings
# Any window size, as a maximized window's page (the screen less the taskbar): check every screen at several.
dotnet run --project tools/GameSync.Snapshots -- <output folder> --data <data folder> --size 1920x1152 glossy-home
# The library with a search typed, and a game's page beside the list with its places, saves and history (--game, or the hero game).
dotnet run --project tools/GameSync.Snapshots -- <output folder> --data <data folder> --game lantern-keep library-search library-game glossy-game
# The design system: serve the offline viewer (http://127.0.0.1:5178), or render cards to PNG at full size with Edge, to compare with the app.
node tools/design-system/serve.js
node tools/design-system/shoot.js <output folder> [--theme dark] [--surface glossy|solid] LibraryScreen GameDetailScreen
# Glossy or Solid on this PC; an open app repaints at once.
& src\GameSync.App\bin\Debug\net10.0-windows10.0.19041.0\gamesync.exe --data <scratch> set surface solid
# The app's icon file and a sheet of the tray icon in every state (copy gamesync.ico to src/GameSync.Tray/Assets; a test checks it's current).
dotnet run --project tools/GameSync.Snapshots -- <output folder> icons
```

- **Real data without touching the owner's**: make a scratch data folder with `gamesync --data <scratch> init --remote <scratch>\cloud --name DESKTOP`, `add-folder E:\Games`, `add-folder G:\`, `scan` (reads only), then `gamesync --data <scratch> art`. Render with `--data <scratch>`, or open the app with it. **Never confirm games in a scratch folder the app opens**: the app's agent syncs confirmed games by itself, and that copies real saves.
- **A synced game with history, safely**: add a stand-in whose saves live in the scratchpad (`gamesync --data <scratch> add-game lantern-keep --title "Lantern Keep" --root saves=<scratch>\fake-saves\Lantern Keep\Saves`), write a file there, `sync lantern-keep`, change it, `backup`, `save lantern-keep "Before the Warden"`, `approve`. Its page then has versions, a named save and a log, and Restore on it writes only into the scratchpad. Render it with `--game lantern-keep library-game`.
- **Windows opened for a test appear in front of the owner**, who may be using the PC: keep them brief and close them after (`Stop-Process` on the scratch app's id; it's not the owner's). On 30 Sep a test window was closed by hand halfway through (most likely by the owner): the app stays in the tray, and starting it again with the same `--data` brings the window back where it was.
- **First run on a fresh scratch folder**: make an empty data folder and copy `savelist.json.gz` and `savelist.etag` into it from a scratch folder that has them (otherwise the first scan downloads the save list). Make a scratchpad games folder with a stand-in: `<scratch>\fr-games\<name>\<name>.exe` (a few KB starting `MZ`) and `Saves\slot1.sav`. Give the program a name no real game has: the save list matches a game in its own folder by its program's name too, so `Lantern.exe` became the real game "Lantern". Start the test copy with `--data <folder>`.
  - Drive it with `tools\window\uia.ps1`: `invoke` for buttons, `toggle` (added 30 Sep) for check boxes and switches, and `picker.ps1` for Add a game folder (picker title "A folder your games") and the cloud folder ("A folder every PC can reach").
  - **Untick every group of real games** (their boxes are named "Untick every game in Sync" and so on) and tick only the stand-in, then **turn both switches off** in Backups and startup before Start using GameSync.
  - The scan itself only reads, and `FirstRun.WindowsSchedule` refuses a data folder that isn't the usual one anyway.
- **Talking to a running app**: the pipe is named `GameSync-` plus the first 20 hex digits of SHA-256 of `<user SID>|<DATA FOLDER, full path, upper case, no trailing \>`; send one line (`status`, `show`, `look`, `quit`) and read one line back. `AppPipe.SendAsync` does it from C#.
- **Commands for the owner** are for Windows PowerShell: a quoted program path needs `&` in front (`& "…\gamesync.exe" scan`), and GameSync must be quit from the tray before a build, or the build can't replace its files.
- **The owner's own GameSync may be running** from `src\GameSync.App\bin\Debug\net10.0-windows10.0.19041.0` (or `src\GameSync.Tray\bin\Debug`) (no `--data`: it syncs their real saves), which locks that folder, so a full build fails to copy there. Leave it running: build a test copy elsewhere with `dotnet build src/GameSync.Tray -o <scratch>\tray-build` (and `src/GameSync.App -o <scratch>\cli-build` for `gamesync.exe`), and run that with `--data <scratch>`.
- **Look at the real window** by capturing it with `PrintWindow` (`tools\window\capture.ps1 -ProcessId <id> -Out <png>`; the window's title is "GameSync"), and at renders with the Read tool on the PNG files; compare with the design system's screens (`design/system/viewer.html`).
- **Drive the real window** through UI Automation from PowerShell (`tools\window\uia.ps1`, with `UIAutomationClient`): find an element by its name, then `SelectionItemPattern.Select()` for a pill tab (`-Action select`) or `InvokePattern.Invoke()` for a button (`-Action invoke`). - **The theme engine's expected values** come from the design system's own JavaScript: `node tests/GameSync.Core.Tests/Fixtures/make-theme-goldens.js` regenerates `theme-goldens.json` after a design-system theme change.

- **A safety refusal is an exception the app must catch** (the safety audit, 7 Oct): a restore throws `BlockedException` or `UnsafePathException` when a rule turns it away; `AppActions.WithServiceAsync` catches them and says why on the game. A new app action that restores goes through it, or catches them too, or the refusal leaves the app's job unseen.
- **A game GameSync starts is followed by its ID, never its handle** (R13): `Process.Start` hands back full access, so `Cli.LaunchAsync` keeps the ID and closes it; `ProcessWatcher.IsRunning(pid, startedUtc)` checks it with query-limited access.
- **Light that keeps moving while a page waits goes on the `Ambient` clock, never an endless `Animation`** (7 Oct): Avalonia's animations tick at the screen's rate (142 frames a second on a 144 Hz screen) and each frame on the CPU renderer costs about 3 ms whatever moved, so one slowly turning ring took half a core. `GAMESYNC_RENDER_STATS=dirty` adds the repainted areas to the frame stats; `tools\window\cpu.ps1 -ProcessId <id>` measures a process's CPU over 10 s (keep its window active). Short motion that ends (a fade, the moment, the banners rising) is fine as an `Animation`.
- **A page's scroller cuts off what spills past a card at its edge** (6 Oct): a `ScrollViewer` clips its content to its viewport, and the cards sit flush with it, so a glow or burst can't pass a card's side however `ClipToBounds` is set inside. What must spill (the Zenith moment's burst) is drawn from the window's `AdornerLayer`, as a free child covering the window that finds its spot each frame with `TransformToVisual` (`GsZenithMoment`).
- **`EffectiveViewportChanged` fires only on a change after you subscribe**: Avalonia remembers the viewport as you subscribe and raises the event only when it differs, so check what's on screen yourself first (`GsAchievementsOverview.WhollyOnScreen`, which intersects every clipping parent), then let the event say when it changes.
- **Capturing a moment in the real window**: PrintWindow takes a frame in about 60 ms, so a loop of frames 30 ms apart shows an animation. In Windows PowerShell, piping a script's output into `Select-Object -First N` stops the script once N lines are out, so keep the output in a variable. A test copy on a scratch data folder quits with `gamesync --data <its folder> quit` alone, as the app's claim and pipe are per data folder; the owner may be at the PC and click in it.
- **Text sizes from resources (A11Y-04, 3 Oct)**: a `FontSize` or `LineHeight` set from `{DynamicResource fs-…}` on text made by a template loses to a class style setting the same thing (the conflict screen's PC name with `Classes="mono"`, a fact's label with `overline`), where a plain number used to win. Give such text no clashing class (set `FontFamily` itself), or a more specific class style after the class's own (`TextBlock.overline.fact-label`). `TextSizeTests` checks every size used is in the scale and none is fixed.

- **Every write to an app-level resource tells the whole window** (KAN-124): setting about 150 `…-color` values one by one on a change of mode was a large part of its cost. Put many values in a `ResourceDictionary` of their own and swap it in `MergedDictionaries` once; recolour brushes in place (`brush.Color = …`), which only repaints. A change of `RequestedThemeVariant` still costs about 80 ms of style work in a debug build.
